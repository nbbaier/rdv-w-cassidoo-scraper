# RSS-only ingestion

The scraper was previously a two-step pipeline: crawl Buttondown's paginated `/archive/` HTML pages to discover newsletter URLs, then fetch each issue's HTML page individually and extract the interview question. We replaced this with a single RSS request to `https://buttondown.com/cassidoo/rss?count=N`, which returns up to N items with full HTML bodies in each `<description>`. Both backlog and weekly ingestion use `count=1000`: the synthetic Number depends on the full oldest-first feed order, so a smaller window is only safe when every returned Issue already exists locally. The trade-off: we depend on Buttondown's `?count=` query param continuing to behave this way — it's undocumented and could be capped or removed unilaterally, at which point the archive-crawl approach would need to be rebuilt from scratch (and won't be in HEAD anymore). We accepted that risk because the single-request shape eliminates pagination guesswork, the per-issue fetch loop, the intermediate `data.json`, and ~half the scraper code.

## Reaffirmed after the static archive investigation, 2026-10-30

Keep RSS as the bulk input. The [source comparison](../research/static-newsletter-source.md) found the same 480 Issue URLs in RSS and Cassidy's static archive index, and current RSS links already target her site. Static HTML retained the sampled historical extraction failure, while no accessible raw Markdown corpus was established in the repository linked from her announcement. The static archive is useful for canonical source links and independent completeness checks; an automated index check is future work, not an existing ingestion dependency.

Preserve the RSS publication date as the existing Question ID. A canonical newsletter URL may use a different, Sunday-normalized date; consuming that link does not authorize renaming Question files. Preserve existing Question bodies and the six hand-maintained historical files during any future source migration.
